# 人事行政问答：低延迟试验与回退

本分支新增后端可选模式，默认关闭；没有修改线上应用配置。普通问答不增加
聊天模型调用或检索轮次，但附加提示词仍有少量输入 token 开销，不能据此承诺
线上耗时完全相同。是否更准确、更快，需要同模型、同知识库的对照实测。

## 开启与关闭

在部署本分支的隔离测试环境，通过已有的应用所有者登录会话调用：

```http
PATCH /api/v1/chats/<chat_id>
Content-Type: application/json

{"prompt_config":{"lightweight_qa":true}}
```

该 PATCH 合并已有 `prompt_config`，不会替换完整提示词和参数。不要用 PUT
仅提交这个字段。读取同一应用配置，确认值是布尔 `true`，而不是字符串。
本模式不自动开启多轮优化或关键词扩展，沿用应用已有的相应开关。

关闭使用同一个 PATCH：

```json
{"prompt_config":{"lightweight_qa":false}}
```

下一次请求恢复原链路。已开始的请求继续使用开始时的配置；关闭开关不会
取消已发出的外部请求。首版未增加设置页面开关，但表单会保留该字段；前后端
应使用同一分支的构建，旧前端保存设置可能丢弃这个新字段。

分支：`feat/hr-qa-lightweight-agent`。保持独立，暂不合并 `main`。没有数据库
迁移，代码回退只需部署上一版本，试验开关在旧版本中不会产生行为。

## 首版的边界

- 普通请求仍执行既有改写、检索、重排和回答，不新增规划/审核模型调用。
- 开启多轮优化时，可靠时间戳之间超过 30 分钟的旧用户话题被切断。当前提问
  仍依赖已过期的“它/那个”等对象时，会请求补充对象。缺少可靠时间戳时保留
  原来的上下文选择，不猜测时间；同一活跃会话的话题切换交给现有改写调用。
- 仅当关键词扩展后的检索没有返回知识块，且查询不同于独立原问题时，才用
  未扩展的独立问题补查一次。知识库、文档限制、元数据过滤和阈值保持一致。
- 补查（含子块归并）的等待预算为 2 秒，每进程最多 2 个进行中的补查，无
  排队。超时、繁忙或错误保留原结果；未找到证据时沿用原有无依据回复。
- 超时不等于底层网络调用被强制中断。慢调用结束前继续占用补查名额，避免
  越超时越堆积。普通检索与生成的既有耗时不计入这 2 秒预算。
- 补查不再追加 TOC 模型调用；深度研究分支没有新增补查层。
- 非空结果不代表内容充分：首版通过回答指令约束意图与条件，不另加语义审核
  模型，也不保证每次都能识别错误证据。知识库缺失仍需补充原始资料。

## 对照验收

使用同一模型、温度、知识库快照和输入历史，分别关闭/开启模式。先测试以下
脱敏问题模式，再使用已获授权的业务样本；不把真实员工资料写进测试代码。

| 场景 | 验收重点 |
| --- | --- |
| Wi-Fi 后隔天问“出差” | 不继承 Wi-Fi；无额外改写调用 |
| 近期追问“它怎么申请” | 保留必要上下文；过期对象应澄清 |
| 中午订餐 | 不把误餐补贴当作订餐流程 |
| 营业执照申请 | 条件式说明借用流程或澄清用途，不先假定新办而拒答 |
| 晚上九点下班是否算加班 | 保留审批、打卡等直接条件，不用餐补门槛判断 |
| 常见明确问题/精确 FAQ | 模型调用和检索次数不增加；引用可对应 |
| 扩展查询为空、原问有结果 | 只补查一次，引用来自实际返回的知识块 |
| 慢检索/大量空结果 | 到预算即返回；容量满时跳过，不排队 |
| 指定文件/元数据过滤 | 补查仍遵守同样的范围 |

分别记录普通路径与补查路径的首个可见文本时间、总耗时（p50/p95）、模型
调用数、检索次数、答非所问、无依据结论及有效澄清。不要把“未找到”表述比例
当作错误率。先对照再决定是否推广；发现明显延迟或答案退步立即关闭开关。

新增日志只记录 `Supplemental retrieval outcome` 与耗时，不新增聊天原文日志。
`recovered` 仅表示返回了知识块，不表示已经人工确认答案正确。
