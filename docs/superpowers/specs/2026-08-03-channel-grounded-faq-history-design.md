# 渠道知识库问答历史隔离与精确 FAQ 设计

## 状态

本设计于 2026-08-03 在对话中确认。用户明确要求先修复历史污染、证据一致性和当前渠道
会话，不实施“操作路径自动转换为流程图”。

## 背景与根因

企业渠道会话 `e905459e77e2923e2bba84c48e7668d4` 已累计 114 条消息。针对“云文档”
和“EHR、培训、绩效系统”的提问，本轮检索及系统提示词分别包含正确答案“余李”和
“钟志斌或者陈国萌”，但回答模型仍复制了历史助手消息中的“IT-陶正浩”和“IT-刘尧”。

当前数据流存在不对称行为：知识库检索在未启用 `refine_multiturn` 时只使用当前问题，
最终生成却携带整个会话中的用户和助手消息。旧助手回答因此绕过本轮检索证据进入生成
上下文，模型可能优先复制语言形式相似但事实错误的历史内容。

## 目标

- 渠道入口最多向聊天服务传递最近两条用户消息，不传递任何历史助手回答。
- 启用多轮改写时，只使用最近两条用户消息生成独立问题。
- 知识库检索和最终回答生成使用同一条当前或改写后的问题。
- 最终生成模型只接收这一条问题，本轮知识块是唯一事实依据。
- 对解析为“问题/回答”对的结构化 FAQ chunk，问题精确匹配时直接返回该行回答，避免
  联系人、系统负责人等短答案被模型改写或替换。
- 备份并清空已污染的当前渠道会话，使后续消息从干净状态开始。
- 保持 Web、OpenAI 兼容接口和其他知识库聊天调用方的响应结构兼容。

## 非目标

- 不自动生成 Mermaid 或其他操作流程图。
- 不修改文档解析、分块、embedding、reranker、相似度阈值或 CSV 源文件。
- 不对非精确 FAQ 问题强行抽取答案；此类问题继续使用现有 RAG 生成。
- 不删除或批量清理其他渠道、用户或会话。
- 不增加数据库字段或迁移。

## 方案比较

### 方案 A：历史隔离 + 精确 FAQ 抽取（选定）

渠道只传最近两条用户消息；聊天服务把它们用于可选的问题改写，但最终生成始终只传一条
独立问题。若召回 chunk 中存在与当前问题规范化后完全相等的“问题/回答”对，则直接使用
该回答并关联对应 chunk。

优点是能从根源隔离错误历史，并对本次 CSV 联系人问题给出确定性结果；普通文档问答仍
沿用现有能力。代价是需要一个严格、保守的 FAQ 解析器。

### 方案 B：仅限制最近若干完整对话轮次

保留最近一至三轮用户和助手消息。改动较小，但最近一轮助手回答本身也可能错误，仍会
成为未经验证的事实来源，不能满足本次修复目标。

### 方案 C：保留完整历史并增加一次 LLM 事实审查

模型生成后再调用模型判断答案是否受知识块支持。该方案增加延迟和费用，审查模型也可能
重复同一错误，而且仍未消除不可信历史进入事实生成的问题，因此不采用。

## 设计

### 渠道历史选择

在 `api/channels/bootstrap.py` 增加纯函数，从持久化消息中倒序选择最近两条 `user`
消息，再恢复时间顺序。系统消息和所有助手消息都不进入 `async_chat()`。完整消息仍按
现有结构持久化，用于审计和前端展示。

当前新消息必定是选择结果的最后一条。若历史中只有当前问题，则只传一条。异常角色或空
内容被忽略，但不会修改数据库中的原始记录。

### 多轮问题改写与生成隔离

在 `api/db/services/dialog_service.py` 将“用于改写的问题”和“用于最终生成的消息”分开：

1. 从输入中取得最近两条用户消息。
2. `refine_multiturn=true` 且存在两条用户消息时，调用 `full_question()` 将它们改写为
   独立问题；调用参数中不得出现助手消息。
3. 未启用改写时直接使用当前用户问题。
4. 检索、结构化 FAQ 匹配和最终生成共同使用这条独立问题。
5. 最终模型消息始终只有一个 `user` 消息，不附加任何历史用户或助手消息。

这条规则只约束带知识库的 `async_chat()` 路径。没有知识库的自由聊天继续保持原多轮
行为。

### 精确 FAQ 回答

新增两个无外部副作用的辅助函数：

- FAQ 解析函数：从 chunk 的 `content_with_weight` 或等价正文中识别重复的
  `问题：...；回答：...` 对。
- 问题规范化函数：执行 Unicode NFKC、大小写折叠、去除空白和句末问号，不进行同义词
  扩展。

对按检索顺序排列的 chunks 逐个处理。当规范化后的独立问题与某个 FAQ 问题完全相等时：

1. 取该行 `回答` 字段的原始文本，去除 CSV 产生的 `Unnamed: ... nan` 尾部噪声。
2. 将对应 chunk 下标作为显式引用交给现有回答装饰流程。
3. 不调用回答模型，避免模型替换联系人或合并其他 FAQ 行。
4. 继续返回现有 `answer/reference/prompt/final` 结构，并复用现有引用规范化逻辑。

若没有精确匹配、解析结果为空或回答为空，则不启用抽取路径，继续现有 RAG 生成。解析器
不得猜测相似问题，避免错误行被确定性返回。

### 会话备份与清理

代码及测试验证通过后，只处理已确认的会话
`e905459e77e2923e2bba84c48e7668d4`：

1. 读取并核对 conversation ID、dialog ID、channel 名称和消息数量。
2. 使用数据库原生导出能力将该行保存到带 UTC 时间戳的备份文件；备份文件不加入 Git。
3. 将该 conversation 的 `message` 和 `reference` 重置为空数组，保留 conversation ID、
   渠道映射、名称及其他元数据。
4. 重新读取数据库确认只有目标会话被更新，并记录备份位置和恢复方式。

任何标识不匹配、备份失败或受影响行数不是 1 时都停止清理。

## 错误处理与日志

- FAQ 正则无法解析某个 chunk：跳过该 chunk，不影响聊天请求。
- 同一问题在多个 chunk 中精确匹配：采用检索顺序最靠前的非空回答，并记录匹配计数。
- 精确答案为空：退回普通 RAG 生成。
- `full_question()` 失败：沿用现有异常处理，不使用助手历史兜底。
- 日志只记录消息数量、是否改写、是否命中精确 FAQ、chunk 下标和会话 ID，不记录完整
  用户问题、完整答案或 chunk 正文。

## 测试设计

### 渠道单元测试

- 114 条混合历史只向 `async_chat()` 传递最近两条用户消息。
- 旧助手消息包含“IT-陶正浩”时，传入聊天服务的消息中不出现该文本。
- 只有当前用户消息时仍正常调用聊天服务。

### 聊天服务单元测试

- `refine_multiturn=false` 时，检索和最终生成只使用当前问题。
- `refine_multiturn=true` 时，`full_question()` 只收到最近两条用户消息，最终模型只收到
  改写后的独立问题。
- 非知识库自由聊天保持现有历史行为。
- FAQ 解析能从截图所示的多行 CSV chunk 中分别提取“云文档”和
  “EHR、培训、绩效系统”的正确回答。
- 问题精确匹配时不调用回答模型，返回原始回答和正确 chunk 引用。
- 近似但不相同的问题不走确定性抽取路径。
- `Unnamed: 2: nan` 等尾部噪声不会进入答案。

### 回归验证

- 运行渠道 bootstrap 单元测试和 dialog service 最终回答测试。
- 运行 Ruff 检查修改的 Python 文件和测试文件。
- 清空会话后依次复测：
  - 云文档相关问题 → `余李`；
  - EHR、培训、绩效系统相关问题 → `钟志斌或者陈国萌`；
  - QMS 查询批料 → 继续返回知识库中的对应回答。
- 检查服务日志，确认本轮生成上下文不含旧助手联系人。

## 验收标准

- 上述两个错误联系人问题返回 CSV 中的精确答案。
- 当前或改写后的问题是检索、精确 FAQ 匹配和最终生成共同使用的问题。
- 带知识库的最终生成消息中不存在任何历史助手回答。
- 普通非精确文档问题仍能走现有 RAG 生成并返回兼容 reference。
- 当前渠道会话有可恢复备份，清理操作只影响一行。
- 不新增或修改任何流程图输出行为。

## 发布与回滚

该修复涉及 Python 后端代码，完成测试后需要重启或滚动更新后端进程才能加载新代码；
知识库文件本身的更新仍不需要重启服务。

代码回滚时恢复对应提交即可。会话需要恢复时，从备份文件按原 conversation ID 写回
`message` 和 `reference`，恢复前再次核对目标行。
