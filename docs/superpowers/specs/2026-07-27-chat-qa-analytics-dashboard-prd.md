# 单聊天应用问答日志看板 PRD

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 产品名称 | 单聊天应用问答日志看板 |
| 文档类型 | PRD |
| 版本 | V1.2 |
| 日期 | 2026-07-27 |
| 适用范围 | RAGFlow 单个聊天应用（`chat_id` / `dialog_id`） |
| 状态 | 已确认 |

## 2. 背景

聊天应用上线后，运营人员需要判断知识库是否覆盖了用户的真实问题，并能够追溯回答最终引用了哪些知识库和具体切片。当前后台已保存会话消息、检索结果和回答引用信息，但缺少面向运营的汇总、筛选和追溯界面。

本需求建设一个单聊天应用维度的问答日志看板，用于：

1. 找出没有命中知识库的问题。
2. 查看每个问题最终引用了哪个知识库及哪些 chunk。
3. 查看过去 30 天和应用上线至今的问答量。
4. 按最终引用知识库筛选问答记录。

## 3. 产品目标

### 3.1 目标

- 让运营人员快速发现知识缺口，定位未命中问题。
- 让运营人员从问题追溯到回答、最终引用知识库、文档和 chunk。
- 准确区分“问题”“问答轮次”和“对话”，避免统计口径混淆。
- 支持按多个最终引用知识库筛选问题级问答记录。
- 提供单聊天应用的近期趋势和累计问答规模。

V1.2 聚焦于“查看和筛选问答日志”，不扩展为知识库维护任务系统。

### 3.2 非目标

V1.2 不包含：

- 跨聊天应用或租户级汇总看板。
- 对模型真实推理过程的因果归因。
- 自动生成或补写知识库内容。
- 对未命中问题进行自动聚类或意图分类。
- 维护任务、负责人、处理状态和修复验证流程。
- 提问人姓名、部门、独立用户数或按员工筛选。
- 仅统计某一种接入渠道。
- 保留已被删除对话的历史统计。
- Agent 应用、搜索应用等其他应用类型的统一分析。

## 4. 核心概念与统计口径

### 4.1 聊天应用

聊天应用由 `chat_id` 标识，在数据库中对应 `Dialog.id`。看板的所有数据必须限定在当前 `chat_id` 下。

统计范围为所有满足 `Conversation.dialog_id = chat_id` 的对话，覆盖该聊天应用在管理后台、企业微信等入口产生的全部问答。查询不得按 `Conversation.user_id` 过滤；企业微信渠道对话的 `user_id` 可能为空，但仍必须纳入统计。

### 4.2 对话

一条 `Conversation` 记录是一场对话，由 `Conversation.id` 标识，通过 `Conversation.dialog_id` 归属于聊天应用。

一场对话可以包含多轮问题，因此：

> 对话数不等于问答次数。

企业微信渠道的对话规则：

- 私聊场景通常由一名企业微信用户对应一场渠道 Conversation。
- 群聊场景通常由一个企业微信群对应一场渠道 Conversation，群内不同成员的问题保存在同一场对话中。
- Conversation 数量不能用于推导提问人数或独立用户数。
- V1.2 只统计全部问题，不展示或筛选具体提问人。

### 4.3 问题与问答轮次

- 数据库存储字段 `Conversation.message` 在接口响应中转换为 `messages`；两者表示同一组消息。
- `message/messages` 中一条 `role=user` 的消息定义为一个问题。
- 用户问题及其后对应的 `role=assistant` 消息构成一轮问答。
- 当前数据中同轮用户问题和回答通常共用相同的消息 `id`，可用于配对。
- `reference` 按问答轮次保存检索结果；解析时还需使用问答轮次顺序进行校验，避免异常历史数据导致错配。
- 只有存在对应最终回答的用户问题才计入“问答次数”。尚未生成回答的孤立用户消息不计入已完成问答统计。

### 4.4 问答发生时间

问答发生时间采用同轮 assistant 消息最终保存的 `created_at`，其含义为回答完成时间。

- 过去 30 天统计按该时间归属到具体日期。
- 时间范围采用连续 30 个自然日，包含当天。
- 时间计算和日期展示使用系统配置时区。
- 若异常历史记录缺少回答时间，该轮仍计入累计总次数，但不计入近 30 天趋势。

### 4.5 有效检索 chunk

满足以下条件的 chunk 视为有效：

1. chunk 为合法对象且具有可识别的 `dataset_id`。
2. `dataset_id` 可追溯到当前聊天应用关联的知识库。
3. 对知识图谱生成的 chunk，`dataset_id` 可以是数组；数组中每个可追溯的知识库均视为该 chunk 的关联知识库。

### 4.6 命中与最终引用

检索命中和最终引用是两个不同概念：

- **检索候选**：本轮 `reference.chunks` 中的全部有效 chunk。
- **最终引用**：最终回答中的 `[ID:n]` 指向的 chunk，其中 `n` 是 `reference.chunks` 的零基索引。

问答状态分为：

| 状态 | 判断规则 |
| --- | --- |
| 已命中且引用 | 存在有效检索 chunk，且回答中至少一个有效 `[ID:n]` 指向有效 chunk |
| 命中但未引用 | 存在有效检索 chunk，但回答中没有可解析的有效引用 |
| 未命中 | 不存在有效检索 chunk |

“最终引用”表示回答明确引用或系统根据回答内容补充引用的支持材料，不宣称能够证明模型推理过程中实际使用了该 chunk。

### 4.7 最终引用知识库

最终引用知识库按以下链路解析：

```text
回答中的 [ID:n]
→ reference.chunks[n]
→ chunk.dataset_id
→ Knowledgebase.id
→ Knowledgebase.name
```

同一轮回答可以：

- 引用同一知识库的多个 chunk。
- 同时引用多个知识库。
- 引用关联多个知识库的知识图谱 chunk。

知识库名称在同一问题内去重展示。

## 5. 用户角色与典型场景

### 5.1 目标用户

- 聊天应用创建者或管理员。
- 知识库运营人员。
- 负责分析知识覆盖率的业务人员。

### 5.2 核心用户故事

1. 作为知识库运营人员，我想查看未命中的问题，以便补充知识内容。
2. 作为应用管理员，我想查看某个问题最终引用了哪个知识库和 chunk，以便核查回答依据。
3. 作为应用管理员，我想选择一个或多个知识库，只查看最终引用这些知识库的问答记录。
4. 作为运营人员，我想查看过去 30 天每日问答量和上线以来累计问答量，以便了解应用使用情况。
5. 作为运营人员，我想看到问题所属的对话，但不希望将整场对话误算成一个问题。

## 6. 功能需求

### 6.1 看板入口与数据范围

- 在单个聊天应用的管理界面提供“问答分析”入口。
- 进入看板后固定使用当前聊天应用的 `chat_id`。
- 用户只能查看其有权管理的聊天应用数据。
- 切换聊天应用时不得残留上一个应用的统计或筛选缓存。

### 6.2 数据概览

页面顶部展示以下指标卡：

| 指标 | 定义 |
| --- | --- |
| 上线至今问答总次数 | 当前聊天应用下所有现存对话中的已完成问答轮次数 |
| 过去 30 天问答次数 | 回答完成时间在最近连续 30 个自然日内的已完成问答轮次数 |
| 未命中问题数 | 不存在有效检索 chunk 的问答轮次数 |
| 检索命中率 | 存在有效检索 chunk 的问答轮次 ÷ 已完成问答轮次 |

补充规则：

- 百分比保留一位小数。
- 分母为 0 时显示 `--`，不显示 `0%`。
- 指标卡显示当前数据更新时间。

### 6.3 过去 30 天问答趋势

- 使用折线图展示最近 30 个自然日的每日问答次数。
- 横轴为日期，纵轴为已完成问答轮次数。
- 无问答的日期补零，保证时间轴连续。
- 鼠标悬停展示日期和准确次数。
- 趋势图统计全部问答，不受下方明细表筛选条件影响。

### 6.4 问答明细表

明细表以“一轮问题”为一行，不以“一场对话”为一行。

默认列：

| 列名 | 内容 |
| --- | --- |
| 问题 | 用户消息内容，单行截断，悬停或展开查看全文 |
| 状态 | 已命中且引用、命中但未引用或未命中 |
| 最终引用知识库 | 由最终引用 chunk 解析出的知识库名称标签；未引用时显示 `--` |
| 最终引用内容 | 最终引用 chunk 的内容摘要；多个 chunk 时显示引用数量，点击查看完整内容 |
| 回答完成时间 | 对应 assistant 消息的 `created_at` |
| 操作 | 查看详情 |

所属对话不占用主表格列，仅在问答详情中展示，用于补充问题上下文。

默认排序：

- 按回答完成时间倒序。
- 缺少回答时间的异常历史记录排在有时间记录之后。

### 6.5 筛选与搜索

明细表提供以下筛选项：

#### 6.5.1 最终引用知识库

- 支持多选。
- 候选项仅展示当前聊天应用关联且用户可识别的知识库。
- 多选条件采用 OR 逻辑：问题最终引用任意一个已选知识库即匹配。
- 若一个问题同时引用多个知识库，匹配后仍展示该问题引用的全部知识库。
- 当前被筛选命中的知识库标签应高亮。
- 该筛选只基于最终引用 chunk，不基于未引用的检索候选 chunk。
- 选择知识库后，未命中和命中但未引用的记录自然不匹配。

#### 6.5.2 状态

- 支持选择：全部、已命中且引用、命中但未引用、未命中。
- 默认值为全部。

#### 6.5.3 问题关键词

- 支持按用户问题内容进行模糊搜索。
- 搜索对象仅为用户问题，不搜索整场对话名称或 assistant 回答。

#### 6.5.4 时间范围

- 支持按回答完成时间筛选。
- 默认展示全部时间。
- 提供快捷选项：最近 7 天、最近 30 天、最近 90 天、自定义。

#### 6.5.5 筛选通用规则

- 不同类别筛选条件之间采用 AND 逻辑。
- 同一多选类别内部采用 OR 逻辑。
- 修改任一筛选条件后回到第一页。
- 支持一键清空全部筛选条件。
- 表格统计数和分页总数必须基于完整服务端数据，不得只筛选当前前端分页。

### 6.6 问答详情

点击“查看详情”后打开抽屉或独立详情区域，展示：

#### 6.6.1 基础信息

- 用户问题全文。
- 最终回答全文。
- 回答完成时间。
- 所属对话名称和会话 ID。
- 问答消息 ID。
- 问答状态。

#### 6.6.2 最终引用

默认打开“最终引用”区域。每个被 `[ID:n]` 指向的 chunk 展示：

- 引用编号，例如 `[ID:1]`。
- 知识库名称。
- 文档名称。
- chunk ID。
- chunk 完整内容。
- 综合相似度、向量相似度、关键词相似度；字段不存在时不展示。
- 知识图谱 chunk 标识及其关联的全部知识库。

#### 6.6.3 检索候选

提供“检索候选”区域，展示本轮所有有效 `reference.chunks`：

- 明确区分“最终已引用”和“未引用候选”。
- 默认按 `reference.chunks` 原始顺序排列。
- 允许展开查看完整内容。

若本轮未命中，详情页展示明确空状态：“本轮未检索到可追溯至当前应用知识库的内容。”

### 6.7 分页

- 明细表必须使用服务端分页。
- 默认每页 20 条。
- 支持切换每页 20、50、100 条。
- 分页总数表示满足当前筛选条件的问题数，而不是对话数。

### 6.8 空状态与异常提示

| 场景 | 展示要求 |
| --- | --- |
| 应用没有问答记录 | 展示“暂无问答数据” |
| 当前筛选无结果 | 展示“没有符合筛选条件的问答记录”，并提供清空筛选入口 |
| chunk 的知识库已删除 | 展示“已删除知识库”及知识库 ID，不得错误归到其他知识库 |
| 引用编号越界 | 将该引用记为无效引用，保留原回答但不生成错误的知识库映射 |
| `dataset_id` 为数组 | 展示所有能够解析的知识库名称 |
| 统计接口失败 | 指标和列表分别展示可重试错误状态，避免整个页面不可用 |

## 7. 页面结构建议

```text
问答分析
├── 指标卡
│   ├── 上线至今问答总次数
│   ├── 过去 30 天问答次数
│   ├── 未命中问题数
│   └── 检索命中率
├── 过去 30 天问答趋势
├── 筛选区
│   ├── 最终引用知识库（多选）
│   ├── 状态
│   ├── 时间范围
│   ├── 问题关键词
│   └── 清空筛选
└── 问答明细表
    └── 问答详情
        ├── 最终引用
        └── 检索候选
```

## 8. 数据与接口需求

### 8.1 数据来源

| 数据 | 来源 |
| --- | --- |
| 聊天应用 | `Dialog.id`、`Dialog.name`、`Dialog.kb_ids` |
| 对话 | `Conversation.id`、`Conversation.dialog_id`、`Conversation.name`、`Conversation.user_id` |
| 问题 | `Conversation.message` 中 user 消息的 `id`、`role`、`content` |
| 回答 | `Conversation.message` 中 assistant 消息的 `id`、`role`、`content`、`created_at` |
| 检索候选与引用映射 | `Conversation.reference` 及每轮的 `chunks` |
| chunk | `id`、`dataset_id`、`document_id`、`document_name`、`content`、`similarity`、`vector_similarity`、`term_similarity` |
| 知识库名称 | `Knowledgebase.id`、`Knowledgebase.name` |

字段转换说明：

- 数据库字段为 `Conversation.message`，会话接口响应字段为 `messages`。
- 数据库字段为 `Conversation.dialog_id`，会话接口响应字段为 `chat_id`。
- 看板服务端应基于数据库字段进行聚合，对外响应可使用现有接口命名风格。

### 8.2 服务端能力

V1.2 应提供面向看板的专用聚合和问题明细接口，不应由前端拉取全部会话后自行统计。

建议能力：

1. **概览接口**
   - 输入：`chat_id`。
   - 输出：累计问答量、近 30 天问答量、未命中数、命中率、每日趋势。

2. **问题明细接口**
   - 输入：`chat_id`、知识库 ID 多选、状态、问题关键词、时间范围、分页和排序。
   - 输出：问题级记录及符合条件的总数。

3. **问题详情接口**
   - 输入：`chat_id`、conversation ID、message ID。
   - 输出：问题、回答、最终引用 chunk 和全部检索候选 chunk。

4. **知识库筛选项**
   - 可复用聊天应用详情中的关联知识库列表。
   - 返回知识库 ID 和当前名称。

### 8.3 服务端解析要求

- 引用标记需要兼容 `[ID:n]` 和现有前端已支持的引用格式。
- 引用索引按零基索引解析。
- 解析最终引用知识库时必须先验证索引范围。
- 同一问题内的知识库和 chunk 均需去重。
- 必须查询当前 `chat_id` 下的全部 Conversation，不得使用 `Conversation.user_id` 限制统计范围。
- `Conversation.user_id` 为空的企业微信渠道对话必须正常参与汇总和明细查询。
- 知识库筛选必须在服务端完成后再分页。
- 接口响应不得返回当前用户无权查看的其他聊天应用数据。
