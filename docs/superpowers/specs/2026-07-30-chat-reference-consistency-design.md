# 聊天引用与来源文件一致性设计

## 状态

本设计已于 2026-07-30 在对话中确认。选定严格策略：回答中的引用编号全部越界时，
不展示任何来源文件，不把检索候选文档冒充为回答依据。

## 背景

研发知识库聊天中，一条“关键工序验证”回答正文只声称引用四份模板，但回答下方展示了
大量无关文件。日志和数据库表明，该轮保存了 10 个 reference chunk，却保存了 25 个
`doc_aggs`。

问题由三个行为叠加产生：

1. 通用检索只把当前页的 Top N chunk 放入 `chunks`，但使用全部达到阈值的候选
   `valid_idx` 生成 `doc_aggs`。
2. 模型输出了 `[ID:42]` 至 `[ID:45]`，而该轮提供给模型的知识块编号仅为 0 至 9。
   后端无法得到任何有效引用下标。
3. 后端在没有匹配文档时回退到完整 `doc_aggs`；前端随后无条件渲染该列表。

因此，问题不只是展示数量过多。当前实现还可能把未支持回答的候选文档标记为来源，
造成引用证据与回答内容不一致。

## 目标

- 聊天回答下方的来源文件只能来自该回答的有效引用。
- 同一文档被多个 chunk 引用时，来源文件只显示一次。
- 引用编号越界时，不显示无效 `Fig.` 标记，也不回退到全部检索候选文档。
- 模型未输出引用时，继续使用现有自动引用插入能力。
- 自动引用仍未找到证据时，返回空 reference。
- 修复 Web 新旧会话页面，并让后端 API、企业微信等其他渠道获得一致的 reference。
- 保持通用检索、检索测试和分页接口现有的完整文档聚合语义。
- 为无效引用和 reference 收缩结果增加不包含正文内容的诊断日志。

## 非目标

- 不调整文档解析、分块、embedding、reranker 或相似度阈值。
- 不在本次修复中解决 `BDMB-YF-223` 至 `BDMB-YF-226` 没有进入当前 Top N 的检索质量
  问题。
- 不修改通用检索接口中 `doc_aggs` 对全部有效候选进行聚合的行为。
- 不回填或批量改写数据库中的历史 conversation reference。
- 不引入新的配置项、特性开关或数据库字段。

## 方案比较

### 方案 A：在聊天响应边界规范化 reference

保留检索层的完整候选聚合，在 `dialog_service` 生成最终回答后校验引用下标，并根据
有效引用 chunk 重新构造 `doc_aggs`。前端增加越界保护，用于处理历史错误数据。

该方案同时修复 Web、API 和渠道输出，且不改变通用检索契约，影响面最小。这是选定
方案。

### 方案 B：检索层仅聚合当前页文档

把 `rag/nlp/search.py` 中 `doc_aggs` 的输入从 `valid_idx` 改为 `page_idx`。实现简单，
但会改变检索测试、搜索分页和其他检索调用方依赖的聚合语义，不采用。

### 方案 C：仅在前端过滤

前端按 chunk 和引用标记过滤来源文件。该方案能隐藏截图中的多余文件，但 API 和渠道
仍收到错误 reference，后端持久化数据也继续不一致，不采用。

## 核心不变量

聊天 reference 必须满足以下不变量：

- 每个有效引用下标 `i` 必须满足 `0 <= i < len(reference.chunks)`。
- `reference.doc_aggs` 中每个 `doc_id` 必须至少对应一个被有效引用的 chunk。
- `reference.doc_aggs` 按 `doc_id` 唯一；相同文件名不能作为唯一性依据。
- `doc_aggs[].count` 表示该回答有效引用中属于该文档的唯一 chunk 数量。
- 回答包含显式引用标记但没有任何有效引用时，`doc_aggs` 必须为空。
- 不得以“没有召回文档”为理由回退到检索层返回的全部候选 `doc_aggs`。
- 无效引用标记不得被前端渲染为可交互的 `Fig.`。

## 后端数据流

### 模型输出显式引用

1. 从可见回答中解析所有 `[ID:n]` 和 `[n]` 引用标记。
2. 将下标分成有效集合和越界集合。
3. 保留有效引用标记；从回答中移除越界标记。
4. 根据有效下标从 `kbinfos["chunks"]` 取得稳定 `doc_id`。
5. 以有效 chunk 为输入重建 `doc_aggs`，按首次引用顺序输出并按 `doc_id` 去重。
6. 有效集合为空时返回 `chunks` 和空 `doc_aggs`。保留 chunks 是为了兼容回答详情、
   调试和既有 API 结构，但这些 chunks 不再被声明为回答来源。

### 模型没有输出引用

1. 继续调用现有 `insert_citations()`。
2. 对自动插入结果执行同一套下标校验。
3. 自动插入得到有效引用时，按有效 chunk 重建 `doc_aggs`。
4. 自动插入仍没有得到有效引用时，返回空 `doc_aggs`，不使用候选聚合兜底。

### 混合有效和无效引用

有效引用继续生效，越界标记被移除。`doc_aggs` 只包含有效引用对应的文档。该场景不会
因为存在一个错误下标而丢弃其余正确证据。

## 后端组件边界

在 `api/db/services/dialog_service.py` 的回答装饰阶段增加两个聚焦的纯函数：

- 引用规范化函数：解析并清理回答标记，返回清理后的回答、有效下标和无效下标。
- 文档聚合函数：接收 chunks 与有效下标，按 `doc_id` 构造最小 `doc_aggs`。

异步向量补取和 `insert_citations()` 仍留在现有 `decorate_answer()` 流程中。纯函数不访问
数据库、不调用模型，便于覆盖边界条件。`rag/nlp/search.py` 的检索聚合逻辑保持不变。

`structure_answer()` 继续负责把内部 chunk 转换为 API reference 格式并持久化，不承担
引用选择职责。

## 前端兼容与历史数据

后端修复只影响新生成或重新生成的回答。为了让已有错误 conversation 在重新打开时不再
展示无效来源，Web 端增加防御性过滤：

1. 从消息正文解析引用标记。
2. 只接受落在 `reference.chunks` 范围内的下标。
3. 正文存在引用标记但有效集合为空时，不渲染 `Fig.`，来源文件列表为空。
4. 有有效引用时，来源文件列表只保留有效 chunk 对应的 `doc_id`。
5. 正文完全没有引用标记时，保留后端 `doc_aggs`，兼容历史上未使用行内引用但明确
   返回来源文件的回答。

该保护应放入共享 citation/reference 工具函数，并由现有和 next chat 页面共同使用，
避免两个页面产生不同结果。前端过滤是历史兼容和防御措施，后端仍是 reference 正确性
的权威来源。

## API 与渠道行为

- Reference JSON 结构不变，继续包含 `chunks`、`doc_aggs`、`total` 和既有可选字段。
- 不需要数据库迁移或 SDK 类型变更。
- 企业微信启用来源文件发送时，只能发送规范化后的 `doc_aggs`。
- 全部引用越界时不发送来源文件；文字回答仍正常发送。
- OpenAI 兼容接口等直接消费 chunks 的路径不改变响应结构，但不得从候选
  `doc_aggs` 推断引用。

## 错误处理

引用错误不应使聊天请求失败：

- 单个引用格式无法解析：原文本不作为有效引用，记录计数，不抛异常。
- 引用下标越界：移除标记，继续处理其他引用。
- chunks 为空：所有引用均无效，返回空 `doc_aggs`。
- chunk 缺少 `doc_id`：该 chunk 不进入文档聚合，记录 warning。
- `doc_aggs` 原始候选缺少字段：不影响重建，因为新聚合只依赖 chunks。

不得在 warning 中记录完整问题、回答或 chunk 正文。

## 可观测性

每轮最终 reference 规范化记录一条结构化日志，至少包含：

- `trace_id` 或 conversation/message 标识；
- `chunk_count`；
- `candidate_doc_count`；
- `explicit_citation_count`；
- `valid_citation_count`；
- `invalid_citation_ids`，限制为去重后的整数列表；
- `final_doc_count`；
- `reference_mode`：`explicit`、`auto_inserted` 或 `none`。

当 `candidate_doc_count > final_doc_count` 时使用 INFO；存在无效下标时使用 WARNING。
日志不包含文件正文、完整回答或用户问题。

## 测试设计

### 后端单元测试

- 4 个有效引用对应 4 个不同文档时，最终只返回这 4 个文档。
- 多个有效引用对应同一 `doc_id` 时只返回一个文档，并正确累计唯一 chunk 数量。
- 有效与越界引用混合时保留有效文档并移除越界标记。
- 10 个 chunk 配合 `[ID:42]` 至 `[ID:45]` 时，最终 `doc_aggs=[]`。
- 显式引用全部越界时不调用“全部候选文档”兜底。
- 回答没有显式引用且自动插入成功时，只返回自动引用对应文档。
- 回答没有显式引用且自动插入失败时返回空 `doc_aggs`。
- chunk 缺少 `doc_id` 时不报错且不生成空 ID 文档。
- 文档名称相同但 `doc_id` 不同时保留为两个文档。
- 阿拉伯数字和波斯数字引用继续按现有规范化规则工作。

### 后端聊天回归

构造 `top_n=10`、有效候选覆盖 25 个文档的场景：

- 返回 chunks 数量仍为 10；
- 回答有效引用两个文档时，`doc_aggs` 数量为 2；
- 回答引用全部越界时，`doc_aggs` 数量为 0；
- 通用 retrieval test 仍能获得原来的完整候选聚合。

### 前端测试

- 有效 `[ID:0]` 渲染 `Fig. 1` 和对应文件。
- `[ID:42]` 在仅有 10 个 chunks 时不渲染交互式 `Fig. 43`。
- 全部引用越界时来源文件列表为空。
- 有效与无效引用混合时只显示有效文档。
- 多个 chunk 指向同一文档时文件卡片去重。
- 没有行内引用的历史消息继续展示后端提供的 `doc_aggs`。
- 现有 chat 和 next chat 对同一输入得到一致结果。

## 验收标准

使用 2026-07-30 的问题“关键工序验证，方案和报告分别用哪两个模板？”复测：

- 页面不再显示 25 个来源文件。
- 当前 reference 只有 10 个 chunks 时，不显示 `Fig. 43` 至 `Fig. 46`。
- 当前检索没有返回 `BDMB-YF-223` 至 `BDMB-YF-226` 时，不把其他候选文件标记为这些
  结论的来源。
- 有效引用场景中的行内 `Fig.`、悬浮 chunk 内容和来源文件卡片保持一致。
- Web、API 和企业微信对同一回答使用一致的来源文档集合。
- 检索测试页面的候选文档聚合数量不因本修复改变。

## 发布与回滚

1. 先合入后端规范化和测试，再合入前端历史兼容保护。
2. 在测试环境复放问题会话，并验证正常有效引用、混合引用和无引用三类会话。
3. 发布后观察无效引用 WARNING、`candidate_doc_count/final_doc_count` 比例及来源文件发送
   数量。
4. 若出现兼容性问题，可回滚前端过滤和后端规范化提交；本方案不涉及数据迁移，回滚
   不需要修复数据库结构。

历史错误 reference 不做数据库回填；重新生成回答或使用新版前端查看时即可获得正确
行为。
