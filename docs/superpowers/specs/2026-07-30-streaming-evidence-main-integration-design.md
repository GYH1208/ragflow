# 流式回复与证据图片主线整合设计

## 状态

本设计已于 2026-07-30 在对话中确认，作为
`2026-07-29-low-latency-reference-image-selection-design.md` 的主线整合补充。

## 背景

`controlled/post-response-evidence` 已实现回答后的可信图片选择，但分支建立后，
`main` 又加入了企业微信长连接流式回复、入站消息标识日志和语音转写。两条分支同时
修改了渠道编排、渠道能力契约和企业微信附件发送路径。

直接选择功能分支会删除流式回复；直接选择 `main` 会继续把引用下标映射出的图片放进
最终流，绕过证据验证。因此必须做语义整合，不能只接受 Git 的任一侧内容。

本次还修正 reranker 超时后的资源生命周期：文字回复必须在 0.9 秒证据预算之外保持
可用，超时任务不得无限占用共享默认线程池，也不得在工作线程仍使用模型时提前关闭
模型。

## 目标

- 保留 `main` 的企业微信流式回复、语音转写和入站消息标识日志。
- 流式及非流式路径都必须先确认文字发送成功，再启动图片证据验证。
- 最终流只能携带文字和已允许的来源文件，不能携带引用下标直接产生的图片。
- 可信图片通过独立的媒体消息发送，最多两张，顺序由证据单元决定。
- 证据处理在 0.9 秒后失败关闭，不延迟或撤回已经发送的文字。
- 超时后仍运行的同步 reranker 调用必须受到全局并发上限约束；模型只能在其全部调用
  真正结束后关闭。
- 未预期异常对外统一为稳定原因码 `rerank_error`，异常类型只进入结构化日志。

## 非目标

- 不修改文档解析、chunk 边界、图片存储或企业微信媒体上传协议。
- 不增加第二次知识库检索、embedding 调用或运行时视觉模型。
- 不保证强制终止第三方同步模型调用；Python 线程不能安全抢占。系统改为限制遗留
  调用数量并拒绝新增工作，避免耗尽共享线程池。
- 不清理现有渠道和对话文件中的全量 Ruff 历史问题。

## 方案比较

### 方案 A：安全语义整合与有界后台执行

保留流式链路，最终流不发送图片；文字确认后执行证据验证。同步 reranker 使用专用的
全局有界执行器和非阻塞容量门控，超时调用完成前持续占用容量并延迟模型关闭。

优点是同时满足流式体验、准确率优先和线程池隔离；代价是执行器满时会保守地跳过图片。
这是选定方案。

### 方案 B：流式场景暂时禁用证据图片

只在非流式路径使用证据引擎。实现简单，但企业微信主要路径无法获得新能力，不满足
本次合并目标。

### 方案 C：保留现有 `asyncio.to_thread` 超时

改动最少，但超时只取消等待，不会终止工作线程；连续慢调用可能占满共享线程池，并且
当前 `finally` 可能提前关闭仍在使用的模型。该方案不可接受。

## 渠道数据流

### 流式路径

1. 读取渠道和对话配置，建立本次 conversation message。
2. 使用 `send_stream(..., finish=False)` 发送占位文本和后续可见增量。
3. 收到最终回答时保存完整 `raw_answer`、`reference.chunks` 和来源文件。
4. 调用 `send_stream(..., finish=True)`：
   - 包含最终文字；
   - 可以包含配置允许的来源文件；
   - `images` 必须始终为空。
5. 只有最终流调用成功返回，才把文字视为已确认发送。
6. 持久化当前 conversation。
7. 若渠道支持引用图片、quote 已启用且存在图片候选，则调用 `EvidenceService`。
8. 按 `conversation_id + message_id` 定向保存 `used_chunk_ids`。
9. 使用稳定 chunk ID 映射最多两张图片，通过 `send()` 发送 text 为空的独立媒体包。

流式启动失败时继续沿现有逻辑降级为完整回复；降级后的完整回复也必须遵循“文字先发、
图片后验”的顺序。

### 非流式路径

非流式路径保留现有证据分支的行为：

1. 生成完整回答并保存 `raw_answer/reference`。
2. 先用 `send()` 发送文字和允许的来源文件，`images=[]`。
3. 只有 `send()` 明确返回 `True` 才启动证据验证。
4. 可信图片以独立媒体包发送。

### 发送确认契约

`Channel.send()` 返回 `bool | None`：支持确认的渠道返回 `True/False`，遗留渠道允许
返回 `None`。`Channel.send_stream()` 在成功完成最终帧时返回 `True`；失败返回
`False` 或抛出异常。只有显式 `True` 可以授权证据工作。

企业微信 WebSocket：

- 普通文字发送在 ACK 成功后返回 `True`；
- 最终流在 ACK 成功后返回 `True`；
- 纯图片/纯文件消息继续由 `_send_websocket_attachments()` 处理；
- 单张媒体失败不阻断后续媒体，但整个文字确认不得由媒体结果替代。

## 有界 Reranker 执行

### 资源模型

新增证据专用的进程级执行资源：

- 固定大小线程执行器，不使用 asyncio 默认共享线程池；
- 容量与最大工作线程数一致，初始为 2；
- 提交前非阻塞获取容量；容量不足时立即返回 `rerank_busy` 并失败关闭；
- 一个回答最多提交两个证据单元，与既有上限一致。

每次 resolution 创建一个模型租约，记录该模型关联的已提交 future 数量。每个 future
结束时递减计数并释放一个全局容量；最后一个 future 结束时关闭 reranker 模型。

### 成功、超时与取消

- 正常完成：收集分数、执行既有阈值和分差规则；最后一个 future 已结束后关闭模型。
- 0.9 秒超时：调用方立即得到 `rerank_timeout`，不等待同步线程；容量在真实线程结束前
  不释放，模型也不提前关闭。
- 协程取消：与超时相同，后台 future 保持受限并在完成后清理。
- 提交部分失败：未提交的单元失败关闭；已经提交的 future 仍由租约回收。
- 执行器满：不排队，直接返回 `rerank_busy`；文字回复不受影响。

同步 Python 线程不能被安全强制停止，所以本设计保证的是“快速返回、隔离线程池、限制
遗留任务数量、正确关闭资源”，而不是虚假的强制取消。

## 错误与可观测性

稳定原因码至少包括：

- `no_visible_evidence_units`
- `no_image_candidates`
- `model_unavailable`
- `rerank_busy`
- `rerank_timeout`
- `rerank_error`
- `below_rerank_threshold`
- `below_rerank_margin`
- `winner_not_cited`

未预期异常的类名和堆栈只记录在日志字段中，对外 resolution reason 固定为
`rerank_error`。日志不得包含完整问题、完整回答或 chunk 正文。

渠道日志继续包含 conversation/message 标识、resolution 状态、used chunk IDs、
image IDs 和耗时；流式路径额外记录最终文字确认结果。

## 测试设计

### 流式整合回归

- 最终流的 `OutgoingMessage.images` 始终为空。
- 最终流成功确认后才调用 `EvidenceService`。
- 事件顺序为：最终文字流 → 证据解析 → 独立图片消息。
- 最终流失败或未确认时不运行证据解析。
- 已验证图片最多两张，并保持证据单元顺序。
- 语音转写输入和入站消息标识日志在合并后继续通过原有测试。

### Reranker 生命周期回归

- 超时在预算内返回 `rerank_timeout`，后台同步调用可以稍后结束。
- 超时返回时模型尚未关闭；后台 future 结束后模型恰好关闭一次。
- 两个占用中的慢调用达到容量上限后，新请求立即得到 `rerank_busy`，不会进入默认
  线程池队列。
- 正常完成、异常和协程取消都释放容量且不会重复关闭模型。
- 任意异常 resolution reason 为 `rerank_error`，日志仍保留异常类型。

### 验证范围

合并前后至少运行：

- 证据引擎、服务、会话持久化、对话最终事件、渠道 bootstrap 和企业微信目标测试；
- `main` 新增的流式回复、语音转写和消息标识测试；
- 新建证据文件的 Ruff 检查；
- `git diff --check`。

## 合并策略

1. 在 `controlled/post-response-evidence` 中合入最新 `main`。
2. 对 `bootstrap.py`、`core/base.py`、`wecom/channel.py` 及对应测试做语义整合。
3. 先用失败测试锁定流式图片绕过和超时资源泄漏，再实施最小修复。
4. 目标验证绿色后提交整合结果。
5. 在主 worktree 将功能分支合并到本地 `main`。
6. 在合并后的 `main` 再运行同一目标套件；绿色后删除功能 worktree 和本地分支。

本次不推送远端。
