# 企业微信 PDF 引用截图过滤设计

## 背景与目标

当前聊天回答的引用 Chunk 可能携带 `image_id`。这些图片既可能是问答文档中的业务配图，也可能是 PDF 解析后生成的页面裁剪截图。RAGFlow 网页聊天和企业微信目前都能消费这些引用图片。

首版需要保留 RAGFlow 网页端的完整引用体验：管理员在网页聊天中仍可查看 PDF 截图。同时，企业微信不得发送任何 PDF 来源的引用截图，但非 PDF 问答文档中的答案配图仍需正常发送。

文字答案、引用标记、来源名称、知识检索和证据解析结果保持不变。

## 已确认范围

- 开关属于企业微信渠道配置，不放在聊天助手设置中。
- 在企业微信 WebSocket 机器人配置中增加“发送 PDF 引用截图”开关。
- 开关默认关闭；关闭时，所有文件名以 `.pdf` 结尾的引用 Chunk 图片都不得发送到企业微信。
- 非 PDF 文档中的引用图片继续按现有规则发送到企业微信。
- RAGFlow 网页聊天、分享页面以及保存的 `reference` 数据保持现状，PDF 截图仍可查看。
- PDF 仍参与检索和回答生成；文字引用和来源信息不受影响。
- 其他聊天渠道不受影响。
- 不新增知识库级或文件级策略，不识别“制度”关键词，也不修改文档解析和索引。
- 已经发送到企业微信的历史图片无法撤回。

## 方案比较

### 方案一：企业微信出站前按 PDF 文件扩展名过滤（采用）

使用引用 Chunk 已有的 `document_name`/`docnm_kwd` 判断来源文件是否为 PDF。在企业微信图片发送列表生成前过滤 PDF Chunk；引用数据本身不修改。

优点是不会影响网页引用展示、会话历史或其他渠道，无需数据库迁移和重新解析知识库，并能保留非 PDF 问答文档配图。

### 方案二：在聊天服务中清空 PDF 的 `image_id`（不采用）

该方案能阻止所有消费者看到 PDF 图片，但也会让 RAGFlow 网页聊天无法显示截图，与“管理员网页可见、企业微信不可发送”的需求冲突。

### 方案三：知识库或文件级权限（后续可选）

为每个知识库或文件增加“允许发送引用图片”策略，可以处理部分 PDF 可发送、部分 PDF 不可发送的情况，但需要新增管理入口和持久化规则。当前已确认企业微信不发送任何 PDF 截图，因此首版不引入这层复杂度。

## 配置与界面

开关保存在对应企业微信机器人的渠道配置中：

```json
{
  "credential": {
    "send_pdf_reference_images": false
  }
}
```

前端在“用户设置 → 聊天渠道 → 企业微信 → 编辑机器人”的 WebSocket 配置项中增加：

- 名称：发送 PDF 引用截图
- 提示：关闭后，PDF 来源的页面截图不会发送到企业微信；非 PDF 文档配图和 RAGFlow 网页引用不受影响。
- 默认值：关闭。

Webhook 模式目前不支持引用图片，因此无需显示该开关。读取缺少该字段的旧企业微信配置时按关闭处理，升级后立即停止 PDF 截图发送。

## 组件边界

### 公共 Channel 层

公共 Channel 提供一个默认允许引用图片的策略方法。该方法接收完整引用 Chunk，而不只接收 `image_id`，从而可以根据来源文档信息决定是否允许发送。其他渠道沿用默认允许行为。

### 企业微信适配器

企业微信 WebSocket Channel 读取 `send_pdf_reference_images` 配置，并覆盖引用图片策略：

- 开关开启：允许 PDF 和非 PDF 图片。
- 开关关闭：拒绝 PDF 图片，允许非 PDF 图片。

### 渠道启动与消息组装层

证据解析仍使用完整引用数据并保存 `used_chunk_ids`。将可信 Chunk 转成 `OutgoingImage` 前调用当前 Channel 的图片策略，只把允许发送的图片加入企业微信出站消息。即使本轮可信证据全部来自 PDF，也只是不生成企业微信图片消息，不改变证据解析和保存结果。

网页端不经过这条渠道出站过滤链路，因此继续使用完整 `reference.chunks` 显示 PDF 截图。

## 数据流

```text
检索得到完整引用 Chunk（含 PDF image_id）
  -> 生成并保存文字回答、reference、used_chunk_ids
  -> RAGFlow 网页端读取完整 reference
       -> PDF 截图继续显示
  -> 企业微信准备引用图片
       -> 根据 document_name 判断来源格式
       -> PDF 且 send_pdf_reference_images=false：跳过
       -> 非 PDF：保留
  -> 企业微信只发送过滤后的非 PDF 图片
```

文字回答仍按现有流程先发送。图片策略在对象存储读取和企业微信素材上传之前执行，因此被拒绝的 PDF 截图不会产生读取或上传请求。

## 文件识别规则

- 优先读取格式化后的 `document_name`，兼容读取 `docnm_kwd`。
- 去除文件名首尾空白后进行不区分大小写的 `.pdf` 后缀判断。
- 文件名缺失或无法判断时不发送该图片，并记录可诊断日志。该策略按“无法确认是非 PDF 就不向企业微信发送”处理，防止异常引用数据绕过限制。
- 不使用 `doc_type`、图片 ID 命名或知识库名称猜测来源格式，因为 `doc_type` 只表示 Chunk 是文字、图片或表格。

## 错误处理与兼容性

- 过滤只影响企业微信本轮出站图片列表，不修改 `reference`、索引数据或对象存储文件。
- 企业微信文字回答必须继续发送，图片过滤不能影响文字发送确认。
- 非 PDF 图片发送失败时沿用现有隔离逻辑，不影响文字回答和后续图片。
- 旧配置缺少新字段时按 `false` 处理。
- “发送引用原文件”是独立设置；本功能只禁止 PDF 截图，不改变原文件发送规则。
- 已经通过企业微信发送成功的历史图片不尝试撤回。

## 测试设计

后端单元测试覆盖：

- 企业微信开关关闭时拒绝 `.pdf`、`.PDF` 等 PDF Chunk 图片。
- 企业微信开关关闭时仍允许 DOCX、XLSX 等非 PDF 问答文档图片。
- PDF 与非 PDF 混合证据时只生成非 PDF 的 `OutgoingImage`。
- PDF Chunk 的 `reference`、`image_id` 和网页可消费数据保持不变。
- 文件名缺失时不发送图片，并产生诊断日志。
- 开关开启时保持现有全部图片发送行为。
- 旧企业微信配置缺少字段时按关闭处理。
- 其他 Channel 的默认图片策略保持不变。

前端测试覆盖：

- 企业微信 WebSocket 配置显示“发送 PDF 引用截图”开关。
- Webhook 配置不显示该开关。
- 新建机器人和旧配置缺省时开关显示为关闭。
- 保存后字段正确写入企业微信 `config.credential`。

## 验收标准

1. 开关关闭时，任何 PDF 来源的引用截图都不会出现在企业微信的新回复中。
2. 同一回答引用非 PDF 问答文档配图时，这些图片仍正常发送到企业微信。
3. RAGFlow 网页聊天和分享页面仍可查看 PDF 引用截图。
4. PDF 的文字内容、引用和来源信息保持可用。
5. PDF 与非 PDF 混合引用时，企业微信只过滤 PDF 图片。
6. 其他聊天渠道行为不变，且无需重新解析知识库或执行数据库迁移。
