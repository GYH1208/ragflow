# RAGFlow API Key 权限分级设计

## 背景与目标

当前 RAGFlow 的 API Key 没有类型、资源范围、有效期和限流配置。Key 通过鉴权后会被映射为所属租户用户，因此现有 Key 可以访问大部分支持 API Key 鉴权的租户 API。公司目前计划由管理员为多个员工配置 WorkBuddy MCP；如果继续使用管理员的现有 Key，员工可以绕过 WorkBuddy 直接调用其他 RAGFlow API。

第一阶段在 RAGFlow 内增加两类 Key：

- **检索专用 Key**：只能检索管理员指定的一个或多个知识库，用于 WorkBuddy MCP。
- **完整访问 Key**：保持现有 API Key 的权限行为，用于管理员控制的可信集成。

改造完成后，管理员可以为 Key 命名、选择类型、配置检索知识库和有效期，并查看基础调用统计。WorkBuddy 不再使用管理员的历史完整访问 Key。

## 已确认的产品规则

- Key 管理页面只对租户 Owner、管理员和系统超级管理员开放；普通成员不能进入 Key 管理流程。完整访问 Key 对现有 Key 管理 API 的访问能力作为第一阶段兼容例外保留，具体风险见后文。
- Key 名称必填，最长 64 个字符，同一租户内允许重名。
- 检索专用 Key 必须选择至少一个知识库，支持多选。
- 检索专用 Key 默认有效期为 90 天，可选 30、90、180、365 天或永不过期。
- 检索专用 Key 固定为每分钟最多 60 次检索，不允许在第一阶段自定义。
- 完整访问 Key 不配置知识库范围，第一阶段不设置有效期和限流。
- Key 第一阶段继续明文存储和展示，不做创建后只显示一次或哈希存储。
- 管理员可以编辑检索专用 Key 的名称、知识库范围、有效期和启用状态；完整访问 Key 可以编辑名称和启用状态。
- 记录 Key 的累计调用次数、检索调用次数、最近调用时间和最近调用结果，但不记录问题原文或逐次调用明细。

## 当前 Key 的兼容定义

现有 `api_token` 表没有 `type` 字段。迁移后，表内所有历史记录均按以下语义处理：

```text
key_type = full_access
legacy = true
```

历史 Key 的内容和现有调用行为保持不变，默认名称为“旧版 API Key”，不设置有效期或限流。管理页面将其显示为“完整访问 Key（旧版）”并展示高权限风险提示。

完整访问表示保持当前 API Key 可访问的 API 范围，并不表示能够访问不支持 API Key 鉴权的内部接口。

## 安全兼容策略

检索专用 Key 不存入现有 `api_token` 表，而是使用独立的 `scoped_api_token` 表。这避免滚动升级或代码回滚期间出现权限提升：旧版本后端不认识新表中的检索 Key，只会拒绝认证，不会把它当成完整访问 Key。

两类 Key 使用不同前缀：

```text
完整访问及历史 Key：ragflow-...
检索专用 Key：      ragflow-rk-...
```

前缀只用于快速路由和运维识别，权限判定始终以后端查询到的记录为准，不能仅信任客户端提交的字符串格式。

## 数据模型

### 现有 `api_token` 表

该表继续存放历史 Key 和新建的完整访问 Key，并增加：

- `name`：Key 名称。
- `is_legacy`：是否为迁移前创建的历史 Key。
- `enabled`：是否允许继续调用。
- `total_calls`：累计调用次数。
- `retrieval_calls`：累计进入检索流程的次数。
- `last_used_at`：最近一次有效 Key 请求的时间。
- `last_result`：最近结果，取值为 `success`、`denied`、`rate_limited` 或 `error`。

历史行在迁移时回填名称和 `is_legacy = true`。新建完整访问 Key 设置 `is_legacy = false`。

### 新增 `scoped_api_token` 表

该表只存放检索专用 Key，主要字段为：

- `tenant_id` 与 `token`：组成复合主键，沿用现有 Key 的租户隔离方式。
- `name`：Key 名称。
- `allowed_dataset_ids`：使用项目已有 `JSONField` 保存知识库 ID 数组。
- `expires_at`：UTC 到期时间；为空表示永不过期。
- `enabled`：启用状态。
- `total_calls`、`retrieval_calls`、`last_used_at`、`last_result`：调用统计。
- 项目标准的创建与更新时间字段。

检索专用 Key 的类型由其所在表确定，不额外保存可被篡改或产生矛盾的 `key_type` 字段。API 响应统一补充 `key_type = retrieval`。

## 统一鉴权与权限判定

Bearer Token 进入鉴权层后按前缀选择对应数据源，加载记录并执行以下流程：

```text
识别 Key
  -> 检查记录是否存在
  -> 检查 enabled
  -> 检查 expires_at
  -> 将 Key 类型和记录放入请求上下文
  -> 检查当前路由是否允许该类型
  -> 检查请求中的知识库资源范围
  -> 执行检索限流
  -> 调用业务接口
  -> 更新调用统计
```

鉴权上下文需要保留当前 Key 记录和认证类型，不能像现状一样只加载对应用户。网页 JWT 请求不受检索 Key 权限规则影响。

完整访问 Key 继续走现有 API Key 逻辑。检索专用 Key 采用默认拒绝策略：所有现有路由默认不可访问，只有明确标记为检索能力所需的路由才能放行。权限声明集中在鉴权装饰器或路由元数据中，避免用分散的黑名单排除危险接口。

第一阶段使用单一 Scope 语义：

```text
knowledge:retrieve
```

这为后续增加只读管理、文档上传或其他专用 Key 留出扩展点，但第一阶段不实现其他 Scope。

## 检索接口和资源范围

WorkBuddy MCP 的检索流程不仅调用 `/api/v1/retrieval`，还会读取知识库列表和文档元数据。因此检索专用 Key 只放行以下能力：

- 读取知识库列表和授权知识库的基础信息。
- 读取授权知识库的文档元数据，用于补充检索结果。
- 调用 `POST /api/v1/retrieval`。

路由权限与资源权限必须同时满足：

- 知识库列表只返回 `allowed_dataset_ids` 中仍然存在且属于当前租户的知识库。
- 请求未传 `dataset_ids` 时，使用该 Key 授权的全部知识库。
- 请求传入的所有 ID 都在授权范围内时才允许检索。
- 只要请求包含一个未授权知识库，整个请求返回 `403`，不能静默过滤后继续执行。
- 读取文档元数据时同样校验路径或查询参数中的知识库 ID。
- 授权知识库已被删除时，列表中忽略该知识库；直接指定它时返回 `404`。
- 检索专用 Key 不能调用知识库、文档或分块的创建、上传、解析、修改和删除接口，也不能访问 Chat、Agent、模型配置、系统管理或 Key 管理接口。

这些限制必须在 RAGFlow 后端强制执行。WorkBuddy 配置、提示词和 Skill 只能改善调用行为，不能作为安全边界。

## 限流

限流只针对检索专用 Key 的实际检索请求：

- 每个 Key 独立计算每分钟 60 次额度。
- 知识库列表和文档元数据读取不消耗检索额度，但计入累计调用次数。
- 使用项目已有 Redis Lua Token Bucket 实现，容量为 60，并按每秒 1 个令牌的速度补充。
- Redis 键使用 Token 的 SHA-256 指纹和固定命名空间，不包含明文 Token。
- 超过额度时返回 HTTP `429`，并提供可重试时间。
- Redis 不可用时返回 `503`，不能跳过限流继续执行检索。

## 调用统计

- `total_calls` 统计已识别且当前有效的 Key 发起的全部 API 请求，包括成功、权限拒绝、限流和业务错误。
- `retrieval_calls` 在请求通过鉴权和限流、真正进入检索流程时增加。
- 未知、停用或过期 Key 的请求不计入统计。
- 请求结束后原子更新计数、`last_used_at` 和 `last_result`。
- 统计更新失败时只记录服务器日志，不改变已经产生的业务响应。
- 第一阶段不保存逐次调用事件、问题文本、员工身份或会话标识。

共享 WorkBuddy Key 的统计只能代表该 Key 的总体使用量，不能用于识别具体员工，也不能把一次检索请求等同于一次用户会话。

## Key 管理 API

现有 Token 列表接口扩展为统一返回两张表的数据，响应至少包含：

- `token`
- `name`
- `key_type`
- `legacy`
- `allowed_dataset_ids`
- `expires_at`
- `enabled`
- `total_calls`
- `retrieval_calls`
- `last_used_at`
- `last_result`
- 创建时间

完整访问 Key 的 `allowed_dataset_ids` 和 `expires_at` 返回空值，方便前端使用统一数据结构；`key_type` 根据记录来源由服务端生成，客户端不能修改已有 Key 的类型。

创建请求示例：

```json
{
  "name": "WorkBuddy-人事知识库",
  "key_type": "retrieval",
  "allowed_dataset_ids": ["dataset-id-1", "dataset-id-2"],
  "expires_in_days": 90
}
```

后端必须重新校验管理员角色、名称长度、类型、有效期选项、知识库存在性和租户归属。检索类型缺少知识库、完整访问类型携带知识库范围或请求字段非法时返回 `400`。缺少 `name` 或 `key_type` 的旧版创建请求同样返回 `400`，不能默认生成新的完整访问 Key。现存 Key 的调用不受这一创建接口变化影响。

第一阶段按已接受的兼容策略，完整访问 Key 仍可调用当前允许 API Key 鉴权的 Key 管理接口。该能力是明确保留的风险：完整访问 Key 不得分发给员工；如果发生泄露，管理员需要立即撤销。后续阶段可以将 Key 管理接口收紧为仅允许管理员网页登录态调用。

## 管理页面

点击“创建新密钥”后打开表单，而不是立即生成 Key。表单包含：

- 必填的 Key 名称。
- 必选的 Key 类型。
- 检索专用 Key 的知识库多选和有效期选择。
- 完整访问 Key 的高权限风险提示。

列表展示名称、明文 Token、类型、授权知识库、创建和过期时间、状态、累计调用、检索调用、最近调用时间及结果，并提供复制、编辑、启停和删除操作。

现有前端部分流程直接使用 `tokenList[0]`。这些流程必须改为按类型选择：Agent、嵌入页面等需要完整权限的功能只能使用完整访问或历史 Key，不能因为列表顺序变化而误用检索专用 Key。没有完整访问 Key 时应显示明确提示。

普通成员不显示 Key 管理入口；后端仍需执行角色检查，不能只依赖前端隐藏。

## 错误处理

- Key 不存在、已停用或已过期：返回 `401`。
- Key 类型不允许访问当前接口：返回 `403`。
- 请求包含未授权知识库：返回 `403`。
- 检索超过每分钟额度：返回 `429`。
- 限流依赖不可用：返回 `503`。
- 授权知识库已经不存在：直接请求返回 `404`。

外部错误响应不需要区分 Key 不存在、停用和过期的具体原因，以免泄露凭据状态；管理页面可以根据管理员查询到的记录展示具体状态。

## 测试与验收

后端单元和集成测试覆盖：

- 历史 Key 迁移后仍按完整访问 Key 工作。
- 新建完整访问 Key 保持现有权限行为。
- JWT 登录行为不受 API Key 权限层影响。
- 检索专用 Key 对未显式放行的路由默认返回 `403`。
- 知识库列表仅返回授权内容。
- 未传 `dataset_ids` 时使用全部授权知识库。
- 请求混入任意未授权知识库时整体返回 `403`。
- 文档元数据读取执行相同的知识库边界检查。
- 第 61 次受限检索返回 `429`，额度恢复后可以继续调用。
- 不同 Key 的限流和统计互不影响。
- 停用、过期和删除后的 Key 无法调用。
- 普通成员不能通过管理 API 创建或管理 Key。
- 统计计数和最近结果在成功、拒绝、限流和错误场景下符合定义。
- Redis 不可用时检索拒绝执行。

前端测试覆盖：

- 创建表单的名称和类型校验。
- 两种类型切换时正确显示或清除知识库和有效期字段。
- 检索类型至少选择一个知识库。
- 列表的类型、状态、权限范围和统计展示。
- 编辑、启停和删除操作。
- 普通成员看不到管理入口。
- Agent 和嵌入页面只选择完整访问 Key。

端到端验收使用真实 MCP 客户端验证连接、工具发现、单知识库和多知识库检索、文档元数据补充、越权拒绝、过期、停用及限流行为。WorkBuddy 中不出现无法解释的认证失败或工具发现失败。

## 上线与回滚

1. 创建 `scoped_api_token` 表，并为现有 `api_token` 增加名称、历史标记、状态和统计字段。
2. 回填历史 Key 的默认名称和历史标记。
3. 部署支持两类 Key 的后端，但在所有节点完成升级前不创建检索专用 Key。
4. 确认所有后端节点均已升级，再部署新的管理页面。
5. 创建用于 WorkBuddy 的检索专用 Key，并选择允许访问的知识库。
6. 在少量 WorkBuddy 客户端验证连接、检索、越权拒绝和限流。
7. 全量替换 WorkBuddy 配置，从员工环境移除管理员完整访问 Key。
8. 根据管理员 Key 的其他用途决定保留或撤销，不再向员工分发。

如果回滚到旧版后端，`scoped_api_token` 中的检索 Key 不会被识别，只会返回 `401`，不会获得完整权限。恢复新版本后可以继续使用原 Key。数据库变更采用新增表和新增列，回滚期间不删除数据。

## 非目标与已接受风险

第一阶段不包含：

- Key 哈希存储、创建后只显示一次或自动轮换。
- IP 白名单、可自定义限流额度或不同 Scope 组合。
- 逐请求审计事件、问题文本、员工身份和会话统计。
- 独立 MCP 网关或新的员工账号权限体系。
- 通过 Skill 或提示词替代服务端权限控制。
- 收紧完整访问 Key 对 Key 管理接口的现有访问能力。

已接受的主要风险是完整访问 Key 仍为明文高权限凭据，并保留现有 Key 管理能力。控制措施是只由管理员保管、不分发给员工，并为 WorkBuddy 单独创建受限 Key。共享检索 Key 只能提供 Key 级统计，无法追踪到具体员工。

## 预估工作量

一名熟悉 RAGFlow 的全栈开发完成数据库、后端权限、Redis 限流、管理页面、自动化测试和 MCP 验收，预计需要约 2～3 周。独立表带来的安全兼容处理预计比直接扩展现有表增加 1～2 人日，但可以避免滚动升级和回滚时的权限提升。
