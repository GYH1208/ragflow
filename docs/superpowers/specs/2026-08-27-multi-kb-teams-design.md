# 多部门团队知识库管理设计

## 状态

- 日期：2026-08-27
- 分支：`feature/multi-kb-teams`
- 目标版本：第一版部门团队功能
- 设计状态：已完成口头确认，等待书面规范复核

## 背景

当前系统把“团队”建立在 `Tenant` 和 `UserTenant` 上。用户注册时会创建一个与用户 ID 相同的 Tenant；知识库的 `tenant_id` 又同时决定所有权、模型配置、文件空间和向量索引命名空间。因此，直接允许一个用户创建多个 Tenant 会把部门成员管理与工作空间、模型、存储和额度耦合在一起。

本功能需要让系统管理员创建 HR、销售、医学等多个部门团队，并把自己拥有的知识库分配给其中一个团队。团队成员可以维护知识库内容，但不能取得知识库所有权或系统管理权限。

## 目标

1. 一个系统管理员可以创建多个部门团队。
2. 一个用户可以加入多个团队。
3. 一个知识库最多分配给一个团队。
4. 知识库所有者始终保留最高权限。
5. 已接受邀请的团队成员可以维护分配给该团队的知识库内容。
6. 只有系统管理员可以管理团队、成员和知识库分配。
7. 保持现有 Tenant、模型配置、文件存储、额度和索引归属不变。
8. 将旧的团队共享数据兼容迁移到“默认团队”。

## 非目标

- 不创建独立的部门 Tenant 或工作空间。
- 不为团队提供独立模型配置、API Token、文件根目录、额度或计费。
- 不设置团队管理员角色。
- 不支持一个知识库同时分配给多个团队。
- 不允许团队成员删除整个知识库、修改核心配置或更换所属团队。
- 不扩展智能体、记忆、搜索应用等其他资源的团队权限模型。

## 核心设计

### 所有权与授权分离

`Knowledgebase.tenant_id` 继续表示知识库所有者的工作空间，并继续用于模型、文件和索引操作。新增的 `Knowledgebase.team_id` 只表示授权范围，不参与存储或索引命名。

知识库必须满足以下不变量：

- `permission == "me"` 时，`team_id` 必须为 `NULL`。
- `permission == "team"` 时，`team_id` 必须指向有效团队。
- 被指向团队的 `tenant_id` 必须与知识库的 `tenant_id` 相同。
- 知识库所有者不依赖团队成员关系，始终拥有完整权限。

### 数据模型

新增 `Team`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `CharField(32)` | 主键 |
| `tenant_id` | `CharField(32)` | 创建团队的管理员工作空间，也是可分配知识库的所有者范围 |
| `name` | `CharField(100)` | 团队名称 |
| `created_by` | `CharField(32)` | 创建该团队的管理员用户 |
| `status` | `CharField(1)` | 有效或失效状态 |
| 基础时间字段 | 继承现有基础模型 | 创建与更新时间 |

`(tenant_id, name)` 建立唯一索引。团队名称使用数据库当前排序规则判断重复，并在服务层先执行去空格和空名称校验。

新增 `TeamMember`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `CharField(32)` | 主键 |
| `team_id` | `CharField(32)` | 所属团队 |
| `user_id` | `CharField(32)` | 被邀请或已加入的用户 |
| `state` | `CharField(16)` | `invited` 或 `active` |
| `invited_by` | `CharField(32)` | 发起邀请的管理员 |
| `status` | `CharField(1)` | 有效或失效状态 |
| 基础时间字段 | 继承现有基础模型 | 创建与更新时间 |

`(team_id, user_id)` 建立唯一索引。第一版没有团队管理员角色；团队管理权由系统管理员身份和团队所有权决定。

修改 `Knowledgebase`：

- 新增 `team_id = CharField(max_length=32, null=True, index=True)`。
- 保留 `permission` 的 `me|team` 值，保持客户端与旧逻辑的兼容边界。
- 不建立数据库外键，遵循现有模型以字符串 ID 关联资源的方式；服务层负责关联完整性。

### 管理权限

团队管理操作同时要求：

1. 当前用户 `User.is_superuser == true`；
2. `Team.tenant_id == current_user.id`。

只有满足这两个条件的管理员可以：

- 创建、重命名和删除团队；
- 邀请或移除团队成员；
- 将知识库分配给团队或取消分配。

管理员只能分配自己拥有的知识库，即 `Knowledgebase.tenant_id == current_user.id`。系统管理员身份不会隐式取得其他用户知识库的所有权或管理权。

团队成员可以接受、拒绝邀请，也可以退出自己已加入的团队。退出不是团队管理操作，只能作用于当前用户自己的成员关系。

### 知识库权限

知识库所有者拥有：

- 查看、检索和使用；
- 上传、修改、删除文档；
- 解析、停止解析、重新索引；
- 管理目录、元数据、切片、标签和知识图谱；
- 修改知识库核心配置；
- 删除整个知识库。

团队分配属于系统治理操作。知识库所有者只有在自身同时是系统管理员时，才能分配或取消团队；普通所有者仍保留知识库本身的最高内容和配置权限。

处于 `active` 状态且 `TeamMember.team_id == Knowledgebase.team_id` 的成员拥有：

- 查看、检索和使用；
- 上传、修改、删除文档；
- 解析、停止解析、重新索引；
- 管理目录、元数据、切片、标签和知识图谱。

团队成员不能：

- 修改知识库名称、嵌入模型、解析器等核心配置；
- 修改 `permission` 或 `team_id`；
- 删除整个知识库；
- 管理团队或成员。

处于 `invited` 状态、已退出、已被移除或团队已失效的用户没有知识库访问权限。未分配团队的知识库仅所有者可访问。

### 权限服务边界

新增集中式团队权限服务，负责：

- 判断系统管理员身份；
- 判断管理员是否拥有团队；
- 返回用户已激活的团队 ID；
- 判断用户是否为知识库所属团队的激活成员；
- 校验知识库和团队是否属于同一个所有者工作空间。

`KnowledgebaseService.accessible`、知识库列表过滤器以及 `check_kb_team_permission` 改为使用该服务。文件访问继续从关联知识库推导权限。解析任务仍使用知识库所有者的 `tenant_id`，不得使用团队成员用户 ID 或 `team_id` 作为索引租户。

## API 设计

### 团队

- `GET /api/v1/teams`
  - 返回当前管理员创建的团队、当前用户已加入的团队以及待处理邀请。
  - 团队条目包含成员数和已分配知识库数。
- `POST /api/v1/teams`
  - 请求：`{"name": "HR 团队"}`。
  - 仅系统管理员可调用。
- `PATCH /api/v1/teams/{team_id}`
  - 请求：`{"name": "新名称"}`。
  - 仅团队所属管理员可调用。
- `DELETE /api/v1/teams/{team_id}`
  - 在事务中把关联知识库更新为 `permission="me", team_id=NULL`，然后使团队及成员关系失效。

### 团队成员

- `GET /api/v1/teams/{team_id}/members`
  - 仅团队所属管理员可查看完整成员列表。
- `POST /api/v1/teams/{team_id}/members`
  - 请求：`{"email": "user@example.com"}`。
  - 只邀请已注册且有效的用户，创建 `state="invited"` 的关系并沿用现有邮件邀请机制。
- `DELETE /api/v1/teams/{team_id}/members/{user_id}`
  - 团队所属管理员可移除成员；当前用户可用相同接口退出自己所在团队。
- `PATCH /api/v1/teams/{team_id}/invitation`
  - 请求：`{"action": "accept"}` 或 `{"action": "reject"}`。
  - 只能操作当前用户自己的待处理邀请。

所有越权访问统一返回授权错误。接口不通过不同错误消息泄露不属于当前用户的团队或知识库是否存在。

### 知识库

知识库创建和修改请求接受：

- 私有：`{"permission": "me", "team_id": null}`；
- 团队：`{"permission": "team", "team_id": "<team-id>"}`。

设置或修改 `team_id` 时，后端必须重新检查当前用户是系统管理员、知识库属于当前用户、团队属于当前用户且团队有效。客户端提交不一致的 `permission` 与 `team_id` 时返回参数错误，不自动猜测或静默修正。

## 前端设计

### 团队管理页

- 页面标题使用“团队管理”。
- 系统管理员看到“创建团队”按钮；普通用户不显示该按钮。
- “我创建的团队”展示名称、成员数、知识库数和管理操作。
- 选中团队后显示成员列表，可邀请或移除成员。
- 管理员可重命名、删除团队。
- “我加入的团队”展示已加入团队和待处理邀请。
- 用户可接受、拒绝邀请或退出已加入团队。

前端隐藏按钮仅用于改善体验，所有权限仍由后端强制校验。

### 知识库页面

- 权限控件从“只有我 / 团队”改为“只有我 / 指定团队”。
- 选择“指定团队”后必须从当前管理员创建的有效团队中选择一个。
- 普通知识库所有者不能创建团队或执行团队分配。
- 知识库卡片显示团队名称标签。
- 所有者看到自己拥有的全部知识库；团队成员只看到其已激活团队下的共享知识库。

## 数据迁移与兼容

数据库初始化流程创建 `team` 和 `team_member` 表，并通过现有 Peewee 迁移机制为 `knowledgebase` 增加 `team_id`。

兼容回填按所有者 Tenant 执行：

1. 找出存在非 OWNER `UserTenant` 关系或 `permission="team"` 知识库的 Tenant。
2. 为该 Tenant 创建唯一的“默认团队”；若已存在则复用。
3. 将 `UserTenant.role == NORMAL` 复制为 `TeamMember.state == active`。
4. 将 `UserTenant.role == INVITE` 复制为 `TeamMember.state == invited`。
5. 将该 Tenant 下所有 `permission="team"` 且 `team_id IS NULL` 的知识库关联到默认团队。
6. 不删除或修改原有 `UserTenant` 关系。

回填以唯一索引和存在性检查保证幂等。它不修改 `tenant_id`，不移动文档、切片、向量索引、文件、模型配置、额度或 API Token。

旧 `/tenants` 接口暂时保留，避免影响知识库之外仍依赖旧 Tenant 团队语义的功能。新部门团队页面和知识库权限只调用 `/teams` 接口。

## 一致性与失败处理

- 创建和重命名团队在服务层预检名称，并捕获唯一索引冲突。
- 邀请成员在服务层预检用户有效性，并捕获成员唯一索引冲突。
- 删除团队使用数据库事务；解除知识库分配失败时不得删除团队或成员关系。
- 知识库分配在更新前锁定或重新读取知识库与团队状态，避免并发删除团队造成悬挂关联。
- 列表与单资源访问使用同一权限服务，避免“列表可见但详情不可用”或反向不一致。
- 团队成员执行解析时，任务和索引上下文始终来自知识库的 `tenant_id`。

## 测试策略

### 模型与迁移

- `Team(tenant_id, name)` 唯一约束。
- `TeamMember(team_id, user_id)` 唯一约束。
- `Knowledgebase.team_id` 可空并建立索引。
- 默认团队迁移复制 active/invited 状态并关联旧团队知识库。
- 迁移重复运行不增加团队、成员或关联。
- 没有旧团队数据的 Tenant 不创建默认团队。

### 服务与接口

- 系统管理员可以管理自己的团队，普通用户被拒绝。
- 系统管理员不能管理其他管理员创建的团队。
- 管理员只能分配自己拥有的知识库。
- 知识库所有者无论是否分配团队均保持完整权限。
- active 成员拥有内容维护权限；invited、退出和被移除成员没有权限。
- 用户可以同时加入多个团队，并看到各团队对应知识库。
- 一个知识库切换团队后，旧团队成员立即失去访问，新团队成员获得访问。
- 删除团队后知识库变为私有，知识库、文档和索引保持存在。
- 团队成员解析、停止解析和重新解析使用知识库所有者 Tenant。
- 越权请求返回统一授权错误。

### 前端

- 创建团队按钮只对系统管理员显示。
- 团队列表、成员列表、邀请、接受、拒绝、退出、重命名和删除交互正确刷新缓存。
- “指定团队”必须选择团队，切回“只有我”清空 `team_id`。
- 普通成员看不到核心配置、团队分配和删除知识库操作。
- 知识库卡片正确显示团队标签。

### 回归

- 运行新增后端定向测试。
- 运行知识库、文档、文件、解析和租户相关测试。
- 运行完整 `test/unit_test`。
- 在具备 Node/npm 的环境运行前端 lint、类型检查和组件测试。

## 发布与回滚

发布顺序：

1. 备份数据库。
2. 执行新增表、字段和兼容回填。
3. 部署后端。
4. 部署前端。
5. 检查 `/api/v1/system/healthz`，并以管理员和普通成员分别验证团队知识库访问。

回滚代码时不删除新增表或 `team_id` 字段。原 `tenant_id`、`permission` 和 `UserTenant` 数据均保留，因此旧版本仍可读取原有工作空间数据。回滚后新部门团队成员不会通过旧逻辑获得知识库权限，这是回滚期间的预期限制，恢复新版本后关系继续有效。

## 验收标准

1. `admin@example.com` 等有效系统管理员可以创建 HR、销售、医学团队。
2. 普通用户不能创建或管理团队。
3. 管理员可以邀请已注册用户，用户接受后加入指定团队。
4. 一个用户可以同时加入多个团队。
5. 管理员只能把自己拥有的知识库分配给一个团队。
6. 团队成员可以维护文档、解析和切片，但不能修改核心配置、分配团队或删除知识库。
7. 知识库所有者始终保留最高权限。
8. 删除团队不会删除知识库及其内容，知识库自动变为私有。
9. 旧团队知识库和成员通过默认团队保持访问连续性。
10. 后端全量单元测试无失败；前端检查在具备 Node/npm 的环境无失败。
