# 企业微信 PDF 引用截图两级开关设计

## 背景与目标

当前系统已经支持向企业微信 WebSocket 机器人发送可信引用图片，并在企业微信渠道配置中提供“发送 PDF 引用截图”开关。该开关默认关闭，可以统一阻止 PDF 来源的页面截图发送到企业微信。

本次改动需要在聊天助手的“高级设置”中增加同类开关，让不同聊天助手可以独立决定是否发送 PDF 引用截图，同时保留企业微信渠道配置作为全局安全限制。

最终规则是：只有企业微信渠道开关和当前聊天助手开关同时开启，PDF 引用截图才可以发送。任意一级关闭时均不发送。

## 已确认范围

- 保留企业微信渠道字段 `config.credential.send_pdf_reference_images`。
- 新增聊天助手字段 `prompt_config.send_pdf_reference_images`。
- 两个开关均默认关闭。
- 旧渠道配置或旧聊天助手缺少对应字段时按关闭处理。
- 两级开关使用“与”逻辑，不允许聊天助手绕过渠道级限制。
- 两级开关只控制 PDF 来源的引用截图。
- 非 PDF 来源的引用图片继续按现有规则发送。
- RAGFlow 网页聊天和分享页面中的引用截图展示不受影响。
- PDF 的检索、回答生成、文字引用和来源信息不受影响。
- “发送引用原文件”保持独立，不受本功能影响。
- 企业微信 Webhook 模式当前不支持引用图片，因此该功能只影响 WebSocket 模式。
- 不新增知识库级或文件级策略，不修改文档解析和索引。

## 方案比较

### 方案一：后端执行两级“与”逻辑（采用）

渠道配置负责全局许可，聊天助手配置负责单个助手许可。企业微信准备引用图片时，同时读取两级设置，仅在两者都为 `true` 时允许 PDF 图片。

该方案不会让聊天管理员绕过渠道管理员设置，API 和前端行为一致，也便于通过日志判断是哪一级阻止了发送。

### 方案二：聊天设置覆盖渠道设置（不采用）

聊天助手开启后直接允许发送 PDF 截图，即使渠道设置关闭。该方案削弱了渠道级安全边界，无法满足“保留两级设置”的要求。

### 方案三：仅在前端合并开关状态（不采用）

前端根据两级设置决定是否展示或提交开关，但后端只校验一个字段。该方案容易被直接 API 请求绕过，并且渠道消息处理进程无法可靠依赖前端状态。

## 配置与界面

### 企业微信渠道设置

继续使用现有配置：

```json
{
  "credential": {
    "send_pdf_reference_images": false
  }
}
```

该字段是企业微信渠道的全局总开关，默认关闭，只在 WebSocket 模式显示。

### 聊天高级设置

在聊天助手的“高级设置”折叠区域增加开关：

- 名称：发送 PDF 引用截图到聊天渠道
- 提示：仅当当前聊天助手和对应企业微信渠道均开启此功能时，才会发送 PDF 引用截图。
- 字段：`prompt_config.send_pdf_reference_images`
- 默认值：`false`

聊天设置的 TypeScript 接口和表单校验模式需要包含该可选布尔字段。加载旧聊天助手时，缺失值在界面和后端均归一化为关闭。

## 组件边界

### 聊天设置前端

聊天高级设置负责展示、校验和保存聊天级开关。它不尝试读取或覆盖企业微信渠道设置，也不在前端推导最终发送权限。

### 聊天配置存储

聊天级字段保存在现有 `Dialog.prompt_config` JSON 中，无需数据库字段或数据库迁移。创建新聊天助手时写入默认值 `false`；读取旧数据时缺少字段等价于 `false`。

### 企业微信渠道适配器

企业微信适配器继续持有渠道级 `send_pdf_reference_images` 设置，并保留按来源文件名识别 PDF 的职责。

图片许可接口需要同时获得当前聊天助手的许可结果。实现时应保持公共 Channel 默认行为不变，避免影响其他渠道。

### 渠道消息处理层

渠道消息处理层已经能够读取当前 `Dialog`。它在可信引用 Chunk 转换为企业微信出站图片之前计算聊天级许可，并与企业微信渠道策略共同过滤 PDF 图片。

两级校验必须发生在对象存储读取和企业微信素材上传之前，避免被拒绝的 PDF 截图产生无效读取或上传请求。

## 权限规则

| 图片来源 | 渠道开关 | 聊天开关 | 结果 |
| --- | --- | --- | --- |
| PDF | 关闭 | 关闭 | 不发送 |
| PDF | 开启 | 关闭 | 不发送 |
| PDF | 关闭 | 开启 | 不发送 |
| PDF | 开启 | 开启 | 发送 |
| 非 PDF | 任意 | 任意 | 按现有规则发送 |

开关只决定图片能否进入企业微信出站消息，不改变证据解析结果、`reference.chunks`、`used_chunk_ids` 或网页端引用数据。

## 数据流

```text
检索得到完整引用 Chunk（可能包含 PDF image_id）
  -> 生成并保存文字回答、reference 和 used_chunk_ids
  -> RAGFlow 网页端读取完整 reference
       -> PDF 截图继续显示
  -> 企业微信准备可信引用图片
       -> 非 PDF：沿用现有发送规则
       -> PDF：读取渠道级开关和聊天级开关
            -> 两者都开启：加入出站图片
            -> 任意一个关闭：跳过
  -> 企业微信发送过滤后的图片
```

文字回答仍先于图片发送。图片被过滤或图片发送失败，均不得影响已经生成和发送的文字回答。

## 文件识别与安全行为

- 优先使用引用 Chunk 的 `document_name`，兼容 `docnm_kwd`。
- 去除文件名首尾空白后，对 `.pdf` 后缀进行不区分大小写判断。
- 文件名缺失或无法判断来源时，沿用现有安全策略，不向企业微信发送该图片。
- 不使用知识库名称、图片 ID 或 Chunk 类型猜测文件格式。
- 非布尔真值不得隐式开启任一开关；只有明确的布尔值 `true` 表示开启。

## 日志与错误处理

当 PDF 引用截图未发送时，日志应能区分至少以下原因：

- `channel_pdf_images_disabled`：企业微信渠道级开关关闭。
- `dialog_pdf_images_disabled`：当前聊天助手级开关关闭。
- 现有的文件名缺失、无可信证据、图片上传失败等原因继续使用既有诊断日志。

如果两级开关都开启但图片读取、上传或发送失败，沿用现有隔离逻辑记录错误，不回滚文字回答，也不删除会话中的引用信息。

## 兼容性

- 旧企业微信渠道缺少渠道字段时按 `false` 处理。
- 旧聊天助手缺少聊天字段时按 `false` 处理。
- 无需数据库迁移或重新解析知识库。
- 现有已经发送到企业微信的历史截图不撤回。
- 网页聊天、分享页面和其他聊天渠道不应用该两级限制。
- 渠道级开关升级后仍保留原有意义，但开启它不再单独构成发送许可。

## 测试设计

### 后端测试

- PDF 图片在两个开关都关闭时不发送。
- PDF 图片在仅渠道开关开启时不发送。
- PDF 图片在仅聊天开关开启时不发送。
- PDF 图片在两个开关都开启时发送。
- 旧聊天助手缺少聊天字段时按关闭处理。
- 字符串 `"true"` 等非布尔值不能开启聊天级许可。
- PDF 与非 PDF 混合证据中，只过滤不满足两级许可的 PDF 图片。
- 非 PDF 引用图片不受两级开关影响。
- 被过滤的 PDF Chunk 仍保留在 `reference` 和证据持久化数据中。
- 文件名缺失时不发送并保留诊断日志。
- 文字发送结果不受图片过滤和图片发送失败影响。
- 其他 Channel 的默认图片策略保持不变。

### 前端测试

- 聊天高级设置显示“发送 PDF 引用截图到聊天渠道”开关。
- 新建聊天助手时默认关闭。
- 旧聊天数据缺少字段时显示为关闭。
- 保存后字段正确写入 `prompt_config.send_pdf_reference_images`。
- 中英文名称和提示文案正确。
- 现有企业微信渠道开关继续显示和保存，不因新增聊天开关而移除。

## 验收标准

1. 只有企业微信渠道开关与当前聊天助手开关同时开启时，PDF 引用截图才发送到企业微信。
2. 任意一级关闭或缺少字段时，PDF 引用截图都不发送。
3. 非 PDF 引用图片继续按现有规则发送。
4. RAGFlow 网页聊天和分享页面仍能读取完整 PDF 引用截图。
5. PDF 的检索、文字回答、引用来源和原文件发送功能不受影响。
6. 被过滤的图片不会触发对象存储读取或企业微信素材上传。
7. 日志可以区分渠道级关闭与聊天级关闭。
8. 升级无需数据库迁移或重新解析知识库。
